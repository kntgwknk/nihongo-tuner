# nihongo-tuner

[![License: MIT](https://img.shields.io/badge/License-MIT-blue.svg)](./LICENSE)

日本語の文章を、日本語のしくみを踏まえて読みやすく自然な文章に整える [Agent Skill](https://docs.claude.com/en/docs/claude-code/skills) です。AI が書いた文章に出やすい癖を数えて減らし、ジャンルに合わせて組み立ても直します。

業務文書、技術文書、記事やブログ、エッセイ、メールに使えます。

AI が書いた文章は、「重要なのは」のような定型の空句よりも、太字・括弧・ダッシュの多用、決め台詞、結論を段落の最後に置く説明調の組み立てで見分けられることが多くあります。作者が AI に書かせた業務資料 26 本を数えたところ、空句は 0 件でしたが、太字が 1,241 箇所、括弧書きが 2,457 箇所、ダッシュが 179 箇所ありました。ただ、こうした癖を消しても、主題の立て方や修飾語の順序といった日本語の文の組み立てが崩れていれば、読みにくいままです。そこで、癖と組み立ての両方を見ます。

## 修正の見本

AI が書いたような社内向けの説明文を、スキルだけを渡したエージェントに直させた実際の出力から選んでいます。

| 直す前 | 直した後 | 見ているところ |
| --- | --- | --- |
| このツールを使用することで、作業時間を大幅に短縮することができると言えるでしょう。 | このツールを使うことで、作業時間を大幅に短縮できるでしょう。 | 冗長な言い回しだけを直し、「大幅に」と推量の「でしょう」は残す |
| 集計ツールは単なる表計算シートではありません。毎月の売上報告の元データを作る仕組みです。 | 集計ツールは、毎月の売上報告の元データを作る仕組みです。 | 誰も言っていない思い込みを先に打ち消す書き方 |
| 売上の入力、入金の消込、経費の登録——こうした作業はすべてこのツールで完結させることができます。 | 売上の入力、入金の消込、経費の登録などの作業は、すべてこのツールで完結させられます。 | ダッシュでつなぐ列挙 |
| 入力項目を減らすことが、回答率を上げる鍵を握っています。 | 入力項目を減らすと、回答率を上げやすくなります。 | 決め台詞を外しても、主張を強めない |

日本語のしくみに当たる直しの例です（`references/japanese-basics.md` と `references/surface-patterns.md` から）。

| 直す前 | 直した後 | 見ているところ |
| --- | --- | --- |
| 新幹線で、普段打ち合わせをしている取引先に向かう。 | 普段打ち合わせをしている取引先に、新幹線で向かう。 | 長い修飾語を先に置く |
| ログ出力を追加した。設定ファイルが読まれ、出力先が決まる。 | ログ出力を追加した。出力先は設定ファイルで決まる。 | 前の文の話題を「は」で受ける |
| 不具合が確認された場合は、報告が求められる。 | 不具合を見つけたら、担当者に報告してください。 | 受け身で消えた動作主を出す |
| そこで役に立つのが、次の 3 つの手順です。 | そこで、役に立つのが次の 3 つの手順です。 | 読点は、文のいちばん大きい切れ目に打つ |

## 使い方

Claude Code のプラグインとして入れる場合:

```
/plugin marketplace add kntgwknk/nihongo-tuner
/plugin install nihongo-tuner@nihongo-tuner
```

スキルの配布ツールを使う場合:

```bash
npx skills add kntgwknk/nihongo-tuner
```

手動で入れる場合は、`skills/nihongo-tuner/` をエージェントのスキルディレクトリ（Claude Code なら `~/.claude/skills/`）にコピーしてください。

あとは「読みやすい日本語にして」「AI っぽいところを直して」「翻訳調を直して」のように頼むか、`/nihongo-tuner <ファイル>` で呼び出します。プラグインとして入れた場合は、プラグイン名が前に付いて `/nihongo-tuner:nihongo-tuner <ファイル>` になります。

### 新しく文章を書くとき

新しく書く文章にも、このスキルの規範を当てられます。使うのは手順の一部です。

1. 書く前にジャンルを決め、`japanese-basics.md` と `surface-patterns.md` を読む。業務文書と技術文書なら `structure-patterns.md` も読む。
2. 書く材料は渡された資料と出典を示せる事実に限る。足りなければ想像で補わず、足りないものを書き手に伝える。
3. 書き終えたら `measure_style.py` で数え、目標に収める。
4. 見本の了承と事実の照合は行わない。代わりに、素材にない事実や数値を書いていないかを確かめる。

### 環境ごとの決まりを足す

スキルのフォルダに `local.md` を置くと、手順に入る前に読んで従います。対象から外すファイルや、ほかのスキルとの使い分けなど、使う環境ごとの決まりを書くためのファイルです。本文と食い違うときは `local.md` を優先します。配布しているこのリポジトリには入っていません。

## 注意点

### スキルが修正の際に守ること

- 事実・数値・識別子・画面文言・コードブロックは変えません。「」で囲んだメニュー名・ボタン名・エラーメッセージも、読み手が画面で探す語なので、不自然に見えても直しません。書き換えの前と後を `check_facts.py` で照合します。
- 挙動についての記述（「〜するとエラーで止まる」など）は、文を組み立て直しても条件と結果の組をずらしません。【要確認】のような未解決の印と、その本文も残します。
- 確信の度合いも変えません。「次回また相談する」を「合意した」にすると、書き手が言っていないことを書き手の言葉として伝えてしまうからです。
- 元の文にない内容は足しません。意味が 1 通りに決まらない語や比喩は、読み方を選んで書き換えず、元のまま残して書き手に確かめます。
- 直すのは理由を言える箇所だけです。「短縮する」を「短くなる」に開くような、より自然そうに見えるだけの言い換えはしません。癖を消そうとして「使う」を「使用する」にするような、硬い漢語への置き換えもしません。
- 太字と括弧は全部は消しません。業務文書と技術文書の太字は、操作を誤ると処理が止まる注意と、取り違えやすい否定にだけ、1 節に 1〜2 箇所まで残します。当たる箇所がなければ 0 にします。括弧は、シート名・セル・ファイルなどの特定、略語の初出、単位、名詞だけの短い補足に残し、中身が文になっている括弧を本文に出します。
- 書き手の声は均しません。エッセイの語り口、引用した話し言葉、敬語の度合いは、読み手が意味を取れる限り残します。
- 人に渡す文章や公開する文章は、見本で直し方の了承を得るまでファイルを書き換えません。
- 「AI っぽさを消した」ことは、本文にも、改訂注記・脚注・コメントにも書きません。

### ジャンルによって変わる点

- 計測の目標値は業務文書と技術文書のための値です。記事とエッセイでは、太字・ダッシュ・決め台詞・空句の 4 つだけを見て、読点と打ち消しは目安にとどめます。
- 結論を先に置く組み立て直しは、業務文書・技術文書・メールに当てます。記事は導入の段落で結論を示せばよく、エッセイには当てません。
- ジャンルが分からないときや混ざっているとき（技術ブログ、社内報のコラムなど）は、読み手と目的を書き手に聞きます。聞けないときは、堅いほうのジャンルに合わせます。

### 苦手なこと

- 計測できるのは表面の癖だけです。語順や主題のぶれは数えられないので、`japanese-basics.md` を見ながら読んで直します。
- 語り口そのものが作品になっているエッセイや小説は、どこまでが意図なのかを書き手に確かめないと直せません。
- 照合スクリプトが拾えるのは、数値・識別子・「」で囲んだ語・コードブロックの変化と、言い換えた語、打ち消しや確信の度合いの語（「必ず」「かもしれ」など）の増減だけです。語の増減に表れない意味のずれ（「相談する」が「合意した」になる、条件を足すなど）は、目で確かめる必要があります。

## 仕組み

1. 対象のファイルを決める。作業ログ・計画ファイル・退避フォルダ・自動生成ファイル・コードは外し、git で管理しているなら、ほかの作業が未コミットの編集を持っているファイルも外す。書き換え前の版は作業ブランチを切るか別の場所に写して残す。
2. ジャンル（業務文書・技術文書・記事・エッセイ・メール）と読み手を決める。ジャンルによって、文末、結論の位置、どこまで直すかが変わる。
3. `measure_style.py` で書き癖を数える（太字、括弧、ダッシュ、決め台詞、打ち消し、冗長な言い回し、読点の偏り、句点の落ちた箇条書きなど）。
4. 代表的な 1 本から 4〜6 箇所を選んで修正前と修正後の見本を作り、方針の了承をもらう。
5. 文の組み立て、語の選び方、表面の癖、全体の構成の順に直す。直しても不自然さが残る箇所は、語の置き換えを繰り返さず、そこで伝えたいことを 1 文で言ってから組み立て直す。短くして意味が伝わらなくなったら、必要な言葉を戻す。ファイルが 4 本以上なら、1 ファイルを 1 エージェントだけが担当する形でサブエージェントに分担してよい。
6. もう一度数え、目標と比べる。業務文書と技術文書の目標は、文になっている括弧が各ファイル 0〜2、太字が 3 つ以上ある節・決め台詞・ダッシュ・冗長な言い回し・読点が 4 つ以上ある文・句点の落ちた箇条書きなどが 0 である。数値は癖を拾う目安で、読みやすさそのものではないので、届いても読み直す。届かなかったファイルには 2 巡目をかける。
7. `check_facts.py` で事実が変わっていないかを照合する。打ち消しや確信の度合いの語が増減した文も候補として出るので、1 件ずつ確かめる。語の増減に表れない変化（「相談する」が「合意した」になるなど）は目で確かめる。
8. 計測の数値の比較、照合で残った差分とその理由、対象から外したファイルを報告する。

| ファイル | 内容 |
| --- | --- |
| `SKILL.md` | 手順 |
| `references/japanese-basics.md` | 日本語のしくみと読みやすさ（「は」と「が」、修飾語の順序、一文一論点、主語の省略、受け身、名詞化、語の種類と表記、文末と確信の度合いなど） |
| `references/genres.md` | ジャンルごとの文末・結論の位置・語り口の許容範囲 |
| `references/surface-patterns.md` | AI の書き癖と翻訳調の一覧と直し方 |
| `references/structure-patterns.md` | 結論先行とグループ化の型と、直しすぎないための決まり |
| `references/do-not-change.md` | 変えてはいけないものと、直してよい範囲 |
| `references/delegation-template.md` | 複数ファイルをサブエージェントに分担するときの依頼文 |
| `scripts/measure_style.py` | 書き癖を数える |
| `scripts/check_facts.py` | 書き換えの前後で事実が変わっていないかを照合する |

スクリプトは、Python 3.10 以上の標準ライブラリだけで動きます。スキルを通さずに単体でも使えます。

```bash
python skills/nihongo-tuner/scripts/measure_style.py draft.md --list
python skills/nihongo-tuner/scripts/check_facts.py --before original.md draft.md
python skills/nihongo-tuner/scripts/check_facts.py --base HEAD draft.md
```

- 文部省「くぎり符号の使ひ方」（1946）：読点を副詞的な語句の前後に打ち、口調の上から要らないものを消すこと、読点で挟んだ語句を飛ばして読む確かめ方
- 文化庁「公用文作成の考え方」、出入国在留管理庁・文化庁「在留支援のためのやさしい日本語ガイドライン」、文化庁「分かり合うための言語コミュニケーション」
- 本多勝一『日本語の作文技術』、木下是雄『理科系の作文技術』、谷崎潤一郎『文章読本』
- 庵功雄「『は』と『が』の一歩進んだ教え方」
- [textlint-rule-preset-ja-technical-writing](https://github.com/textlint-ja/textlint-rule-preset-ja-technical-writing)、[textlint-rule-preset-ai-writing](https://github.com/textlint-ja/textlint-rule-preset-ai-writing)
- [natural-japanese](https://github.com/coji/natural-japanese)（coji・MIT）：確信の度合いを変えない規則、打ち消しの分類、直しすぎについての評価結果
- [AI の謎な説明文を直すスキル](https://zenn.dev/microsoft/articles/explain-before-shorten)（Kazuki Ota・Zenn）：縮めすぎた表現を実際の動きの文に戻すこと、行動を求める否定を肯定形にすること、直らないときは伝えたいことから組み立て直すこと
- [yomiyasu](https://github.com/nanaism/yomiyasu)（nanaism・MIT）：書き換えで打ち消しの有無や確信の度合いが変わっていないかを照合すること
- ダンク「わかりやすい文章構成のコツ」

考え方を参考にした資料で、文や例文は写していません。例文はすべて、このスキルのために作った架空のものです。各資料の URL と、どの規則の根拠にしたかは `references/` の各ファイルに書いてあります。ただし yomiyasu と Zenn の記事は上の説明と URL だけで、natural-japanese は `structure-patterns.md` に評価結果を引いているだけです。
