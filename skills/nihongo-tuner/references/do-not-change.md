# 変えてはいけないもの

文体を直す作業で事実が変わると、資料が実物と食い違う。次のものは不自然に見えても変えない。`scripts/check_facts.py` は、このうち機械で拾えるもの（1〜4）を書き換えの前後で照合する。

## 1. コードブロックの中身

画面に出るダイアログ文言・ログ・設定値・図をそのまま写したもの。空行も文言の一部である。

## 2. バッククォート内の識別子

シート名、関数名、名前付き範囲、ファイル名、列の項目ID、コミット前のブランチ名など。表記ゆれに見えても、実物の綴りに合わせてある。

## 3. 数値

列数、件数、行番号、日付、金額、実行時間、上限値。「約」「程度」などの幅の表現も、実測の精度を示しているので変えない。

## 4. 「」で囲んだ語

メニュー名、ボタン名、エラーメッセージ、画面の見出し。読み手はこの語で画面を探す。

## 5. 技術的な主張

「〜するとエラーで止まる」「〜はエラーが出ない」「〜は 5 分遅れる」のような、挙動についての記述。文を組み立て直すときに、条件と結果の対応をずらさない。特に、グループ化で「変えたときに起きること」を1か所にまとめるとき、どの条件でどの結果になるかの組を崩さない。

## 6. 未解決事項の印

【要確認】などの印と、その本文。

## 7. 確信の度合いと、元にない内容

`check_facts.py` では拾えないので、書き換え後に目で確かめる。

- 確信の度合いを変えない。「来週あらためて検討する」を「決定した」に、「〜の見込み」を「〜する」にしない。反対に、言い切っている文を「〜と思われる」に弱めることもしない。
- 見出しや冒頭の要約で、本文の条件を落とさない。本文が「平日の 18 時までに申し込んだ分は翌営業日に発送」と書いているなら、見出しを「翌日発送」にしない。条件が込み入る節は、「発送の時期」のように何の話かだけを示す見出しにする。
- 元の文にない条件・理由・様子・程度・時期を足さない。言い換えで足してよいのは、元の語がもともと含んでいる意味を言葉にする分だけである。元の文書のどこにも書かれていないことは、もっともらしくても書かない。
- 比喩や独自の言い回しは、語そのものの意味をふだんの言葉で言えるなら、その語だけを言い換える。「静かに止まる」は「気づかないうちに止まる」、「工数が溶ける」は「工数が無駄になる」、「原因を潰す」は「原因を取り除く」、「設定が効く」は「設定が有効になる」。何を指すか・何をすることかが元の文書から決まらないものは、元の語のまま残す。指す先のない語（「片方」「この境界」）、中身の分からない比喩（「解像度を上げる」）、前後とつながらない標語が当たる。元の語のまま残すのは語の意味であり、文末は残さない。「です・ます」と「だ・である」は `surface-patterns.md` §8に従ってそろえる。残した語は、読み方の候補を報告に書いて書き手に聞く。言い換えたあとも主語や対象が分からないときは、言い換えたうえで、分からない点だけを聞く。
- 元にない数の枠組み（「理由は 3 つある」）、まとめの節、一般論の注意の段落を足さない。
- 元の文に動作をする人が書いていなければ、推測で書き足さない。必要なら書き手に確かめる。
- 1文を2文に分けるときは、元の文に無かった「したがって」「ところが」のような接続詞を足さない。元の文の「〜ので」「〜けれど」が示していた関係は、分けたあとも同じ語で残してよい。

| 修正前 | 内容を足した直し | よい直し |
| --- | --- | --- |
| 同期は止めない。動かしたまま直す。 | 同期は、あらかじめ止めません。動かしたまま、必要なら直します。（「あらかじめ」「必要なら」は元の文にない） | 同期は止めません。動かしたまま直します。 |
| 放置すると集計が狂います。 | 放置すると、エラーが出ないまま集計が少しずつ狂います。（エラーの有無と進み方は元の文にない） | 放置すると集計が狂います。（直す所がないので変えない） |
| 権限まわりの解像度を上げる。 | 権限の仕様を細かく把握する。（読み方を1つ選んでいる） | 権限まわりの解像度を上げる。（残して、「解像度を上げる」が何をすることかを書き手に聞く） |

## 8. 直すのは、理由を言える箇所だけ

直すのは、`surface-patterns.md` の癖か `japanese-basics.md` の項目のどれに当たるかを言える箇所だけにする。理由を言えない語の置き換えはしない。より自然そうに見える言葉への言い換えも、理由がなければしない。

- 漢語を和語に開く（「短縮する」を「短くなる」に）、他動詞を自動詞に変える、「〜ことで」を「〜と」に変える、といった言い換えも、理由がなければしない。
- 1つの文に癖が1つあっても、直すのはその癖の部分だけにする。文全体を書き直さない。
- 修正前後の例文に形が似ているだけでは、その直し方を当てない。例文と同じ癖に当たるかを先に確かめる。

| 修正前 | よい直し | 直しすぎ |
| --- | --- | --- |
| 新しい申請画面を活用することにより、記入漏れを大幅に減少させることができると言えるでしょう。 | 新しい申請画面を使うことにより、記入漏れを大幅に減少させられるでしょう。 | 新しい申請画面を使えば、記入漏れはぐっと減るでしょう。 |

よい直しで変えたのは、「活用する」（ただ使うことを大きく言った漢語）、「させることができる」（冗長）、「と言えるでしょう」（冗長な推量。「でしょう」で推量は残る）の3か所だけである。直しすぎの例は、「〜ことにより」と「大幅に減少させる」まで理由なく変えている。「使用する」「確認する」のように文書でふつうに使う漢語は、硬く見えても和語に開かない。

## 境界事例

| 事例 | 扱い |
| --- | --- |
| 本文で「」付きの語を、太字に変えたい | 変えない（「」は画面文言の印として使われている） |
| 同じ文が2回あるので1回削る | 削ってよい。`check_facts.py` の差分に出るが、残ったほうに同じ事実があれば問題ない |
| 括弧内の数値（「（最長 5 分）」）を本文に出す | 数値を変えなければよい |
| 画面文言の言い回しが不自然 | 資料側では直さない。コードの文言を変える別作業にする |
| 表の空欄の「—」 | ダッシュの除去対象にしない |
| コードブロックに描いたフロー図の飾りの絵文字 | 外してよい（画面文言ではない）。`check_facts.py` の差分に出るので、絵文字以外が変わっていないことを確かめる |
| メニュー名そのものに絵文字が入っている（「🛠️GASツール」など） | 残す。コードの `createMenu` の引数で確かめる |
| 見出しに社内語が入っている | 見出しの階層と番号は変えずに、語句だけ直してよい。見出しへのリンク（`#` のアンカー）があれば追従させる |
| 仕様書で定義して使っている技術用語が、社内語の一覧に当たる（「縮退」など） | 開発者も読む仕様書なら残してよい。マニュアルでは平易な言葉にする |
| 「」で囲んでいるが画面文言ではない、著者の言い回しの引用 | 言い換えてよい。`check_facts.py` の「画面文言」に差分が出るので、コードに同じ文字列がないことを確かめてから直す |
